- S1 findings so far (nuc3 probes, oneAPI 2026.1.1 runtime as bundled):
  * default L0 mode here is BATCHED command lists: a host-USM flag written by a kernel is never seen unless something
    queries an event. UR_L0_USE_IMMEDIATE_COMMANDLISTS=1 fixes it. The level_zero v2 adapter gave stale host-USM data: avoid.
  * host USM is coherent only at kernel boundaries (1-way: the GT L3 is not invalidated by CPU stores while a kernel
    runs; even system-scope atomics in a running kernel never saw a CPU store -> a GPU spin/mailbox kernel cannot work,
    and a 3 s spinning kernel = GPU HANG + device lost). In-kernel completion flags (fence + atomic counter) gave stale rows.
    => zero copy with hand-over at command boundaries only: CPU writes x/ids before submit, reads rows after the event.
  * kernels reading x / writing rows in host USM: 0 mismatches over 3000 iterations; per-kernel boundary ~23-35 us.
  * GPU read bandwidth host USM == device USM (38 vs 37 GB/s on nuc3); CPU reads host USM at malloc speed
    (i915 GEM mmap, write-back, 4 KiB PTEs only: no 2 MiB pages from this runtime).
  * limited SYCL graphs are supported (ext_oneapi_limited_graph); full graphs not.
