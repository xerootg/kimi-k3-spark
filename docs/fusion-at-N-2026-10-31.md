# Production fusion and exact decode columns

Scope: GLM-5.3 quantized decode on GB10, one token per sequence, N=1..8. Sources are the supplied `evidence/c-tree/ggml/src/ggml-cuda/ggml-cuda.cu` and `evidence/c-tree-extra/ggml/src/ggml-cuda/` leaves. File references below are relative to those CUDA directories. Local `llama/` leaves are identified explicitly. No GPU launch trace is available here.

## What FD10 versus FD40 actually establishes

At decode step 1, FD10 has 10,401 records and FD40 has 10,422, including output/sample. Every operation count is equal except TOP_K (21 versus 0), ARGSORT (149 versus 170), VIEW (2432 versus 2453). FD10 includes all 387 RMS_NORMs and 557 MULs, all 957 ordinary MUL_MATs, 450 MUL_MAT_IDs and 228 GLUs; FD40 has exactly those same counts. Both include router UNARY/ARGSORT/GET_ROWS/SUM_ROWS/CLAMP/DIV intermediates. Thus these traces **do not exhibit the proposed disappearance of fusion interiors**. The 21 extra VIEWs are the ARGSORT-top-k slice, not evidence of CUDA fusion.

0034's digest callback asks to read every eligible intermediate. The local scheduler in `llama/ggml/src/ggml-backend.cpp:1899` creates a backend graph view ending at each requested tensor. Such graph boundaries prevent fusion across requested intermediates. A production-configuration run with this callback is not a fusion-transparent launch trace. The source inventory below is exhaustive for the supplied fusion dispatcher; its GLM entries are candidates, not measured selections. Establishing the exact production launch list requires a fusion-site log/profile with the digest callback disabled.

Step-0 logits are d6bf1d66a423a0d1 (FD10) versus f7b741495679b61a (FD40). At step 1 the first unequal tensor is already node_2 DUP, before attention norm. The initial state has diverged; this cannot isolate a particular decode fusion as the cause. 0035 also affects small-column prompt matmuls, and old 0036 changed singleton indexer selection.

`ggml_cuda_check_fusion_memory_ranges`, graph-use checks, contiguity and stream/concurrency guards still apply. v3 introduces no global fusion prohibition. Dense column-sensitive matmul fusions run as singleton fused calls, while row-local fusions retain production graph matching. This does not constitute a universal solution for arbitrary shape-dependent fusion eligibility in other architectures.

## 0036 v2 selection and attention

The N=1 branch retains `ggml_cont(ggml_top_k(...))` exactly. Only N=2..8 with n_seqs_unq==n_tokens builds N singleton TOP_K nodes on contiguous score-row views, then concatenates/reshapes integer indices to the original shape. Single-sequence prompt graphs remain unchanged. This uses the same production singleton TOP_K dispatch and scratch allocator, avoiding a claim that ARGSORT has equivalent boundary ties. Normal router fusion remains intact.

The production top-k leaf/build CCCL version is missing. The local leaf selects CUB DeviceTopK with explicitly nondeterministic unsorted output on newer CCCL, and its radix gather can race on boundary ties. Replaying the same singleton kernel eliminates batch dispatch differences; it cannot prove deterministic membership for an intrinsically nondeterministic singleton kernel. Equal selected sets require a GB10 measurement (or an owner-approved production kernel change). The per-row TOP_K graph preserves whichever kernel the installed production backend uses.

Attention keeps the existing 0036 per-query/per-stream singleton FA graph nodes only for multi-sequence decode. Equal KV visibility/extent/padding remains a prerequisite; slicing does not shrink the physical KV extent.

## Verification and window

`python3 tests/check-fusion.py` checks 0018→0010→0008→0034v2→0035v3→0036v2, reverse checks, the fd4 old-pair replacement sequence, production graph/model C++17 syntax, real FA constructors, and real TOP_K constructors across N=1..8, prefill128 and all row axes. `python3 tests/check-fusion-dispatch.py` executes the actual fused wrapper with host launch spies to check singleton geometry, F/Q calls, bias/GLU preservation, token-axis slicing, higher strides and scatter. These are host tests; no CUDA compiler or GB10 runtime was available.

`win2fdg2.sh` copies ~/llama-k3-fd4 to ~/llama-k3-fdg2, reverses 0036/v1 then 0035/v2, applies/checks v3/v2, relocates generated build text and incrementally builds llama-server. It preserves G0..G4 and three G5 rounds; G4 repeats G3's flags with fusion on, G5 uses G3 flags plus expert split-cols, A submitted first and B three seconds later. The script unsets inherited DISABLE_FUSION and never sets it. G0 must pass the available historical gold MD5 prefix (9449ae5738); all legs additionally compare full content bytes against fresh G0. No full historical gold content/hash was supplied, so the historical-prefix control is weaker than a historical full-byte comparison. This window measures completion content, not equality of every logit byte; tensor/launch tracing needs a separate fusion-transparent diagnostic.
